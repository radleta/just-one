# Release process

1. **Be on an up-to-date `main`.** `git checkout main && git pull`. Work reaches `main` through
   develop-to-main pull requests, so a local `main` usually lags. A tag cut anywhere else fails the
   publish: the step "Verify tag is on main branch" in
   [`.github/workflows/release.yml`](../../../.github/workflows/release.yml) rejects a tag whose
   commit is not on `origin/main`.
2. **`npm run release:prepare`.** Its steps are in `package.json` `scripts`; the package check is
   [`scripts/verify-package.js`](../../../scripts/verify-package.js).
3. **Bump, tag and push.**
   - `npm run release` lets standard-version pick the bump from the conventional commits, update
     `CHANGELOG.md`, commit and tag. Its `postrelease` script then pushes the commit and the tags.
   - `npm run release:minor` and `npm run release:major` do the same but **do not push**: npm runs a
     `post` script only for the script of exactly that name, and there is no `postrelease:minor`.
     Push yourself afterwards: `git push && git push --tags`.
   - A "Bypassed rule violations" message on the push to `main` is expected, not an error.
4. **The tag push publishes.** `release.yml` builds, publishes to npm with provenance, and creates
   the GitHub release. Confirm the workflow passed before announcing the version: npm can take a
   minute or two to list it.
5. **Bring `develop` level with `main`.** `git checkout develop && git pull && git merge main &&
   git push`, so the release commit and tag are on `develop` too.

`CHANGELOG.md` is generated by standard-version: never edit it by hand. CI and the commit hooks are
[repo-tooling](repo-tooling.md).
